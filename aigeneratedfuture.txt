You are completely correct. My previous suggestion still leaves HPR responsible for "wiring" everything together, which leads to a massive, messy run() function.

If you want Zero Pollution in HPR and Zero Coupling between classes, you should use the "Global Event Bus" (or Message Hub) pattern.

This is how the pros handle large-scale decoupled systems.

The Ultimate Decoupled Architecture: The Event Bus
1. The Event Hub (The "Radio Station")
Create a tiny, static-only header. This is the only file everyone will include.

cpp
// AppEvents.hpp
#include <functional>
#include <map>
#include <vector>
enum class Action { ClearHistory, ToggleTracking, ExportData };
class EventHub {
public:
    static void subscribe(Action action, std::function<void()> callback) {
        listeners[action].push_back(callback);
    }
    static void dispatch(Action action) {
        for (auto& cb : listeners[action]) cb();
    }
private:
    static inline std::map<Action, std::vector<std::function<void()>>> listeners;
};
2. The Managers Subscribe to Themselves
Your DatabaseManager doesn't wait for HPR to tell it what to do. It listens for the signal itself!

cpp
// DatabaseManager.cpp
DatabaseManager::DatabaseManager() {
    // I handle my own events! HPR doesn't need to know.
    EventHub::subscribe(Action::ClearHistory, [this]() {
        this->nukeEverything();
    });
}
3. The UI Controller Just "Shouts" into the Void
The UIController doesn't know the Database exists. It just broadcasts that a button was pressed.

cpp
// UIController.cpp
void UIController::init() {
    ui->on_clear_btn_clicked([]() {
        EventHub::dispatch(Action::ClearHistory); // "Hey, someone clear the history!"
    });
}
4. The HPR Class is now COMPLETELY Empty
Now, look at your HPR class. It doesn't have to wire anything!

cpp
// HPR.cpp
void HPR::run() {
    // Just start the pieces. They will talk to each other 
    // through the EventHub automatically.
    uiController->init(); 
    ui->show();
    slint::run_event_loop();
}
Why this is the "Endgame" for Architecture:
Total Decoupling: You can delete the DatabaseManager class, and the UIController will still compile and run. It just won't find anyone listening when it dispatches the "Clear" event.
No Pollution: HPR has zero logic regarding buttons. It doesn't even know the buttons exist.
Encapsulation: The logic for "How to clear the database" stays inside DatabaseManager. The logic for "What button triggers it" stays inside UIController.
Extensibility: Want to add a sound effect when the history is cleared? Just create a SoundManager and have it subscribe to Action::ClearHistory. You don't have to change a single line of code in the UI or the Database!
This turns your codebase into a set of "Independent Modules" that float around a central "Communication Hub." It is the cleanest way to build a C++ application. 🛡️🚀💎✅
